# 精简产品 PRD

## 核心原则

始终从产品角度定义用户场景、产品规则和可见结果。让产品可以确认方案、研发可以理解预期、测试可以判断对错，但不替研发设计实现方式。

PRD 固定使用四个一级模块：

1. 简介
2. 产品概述
3. 产品需求详解
4. 数据兼容问题

详细写法见 [PRD 写作指南](references/prd-writing-guide.md)。开始写作前必须阅读该文件。

## 工作流程

1. 阅读需求材料、原型、现有文档和评审意见，区分已确认规则、示例和待确认内容。
2. 提取当前痛点、本次变更和目标；背景不单列当前做法，也不解释痛点影响。
3. 梳理角色、使用端、功能关系、用户流程和本次功能点。
4. 按功能点逐项编写需求详解；每个功能点只写适用的基本定义、交互方式、数据展示、空值和异常。
5. 判断新版本对已有数据、配置和历史内容的产品影响，写入数据兼容问题。
6. 删除重复说明、无效铺垫和内部实现，统一名称并核对原型、字段和数量。

## 输出规则

- 原型负责表现布局，文字只补充原型无法表达的规则和状态变化。
- 同一规则只定义一次；其他模块需要时引用，不换一种说法重复。
- 功能点是变更目录，只写“改什么、用户能做什么”；详细规则放到对应需求详解。
- 使用明确的产品语言。未确认内容标记为待确认，不用“可能、适当、如有需要”等模糊表达代替决策。
- 字段名称以指定的数据标准为准。PRD 可列展示名称、类型和默认状态，不复制接口定义或另建字段标准。
- 只有实际涉及的状态、权限和边界才写入对应功能，不机械增加固定章节。
- 数据兼容只描述新旧版本下用户看到什么、能否继续使用、是否需要操作，不描述迁移程序。

## 产品与技术边界

PRD 可以写“自动获取数据、加载中、获取失败、允许重试”，因为这些是用户可感知的产品行为。

PRD 不写接口顺序、错误码、数据库、缓存、对象结构、前后端分工、事件监听、存储方案、迁移脚本、版本字段、幂等或回滚机制。若原材料包含这些内容，只保留其对应的产品结果。

## 交付前检查

- 四个一级模块齐全，且没有额外的“痛点”“范围与非范围”等固定一级模块。
- 背景只包含当前痛点和本次变更；目标只描述本次改动及预期结果。
- 产品概述中的每个功能点都能对应一项需求详解。
- 默认状态、操作结果、数据展示及必要的空值和异常已经明确。
- 同一对象全文名称一致；原型、文字、字段和数量没有冲突。
- 历史数据影响已说明；不受影响时用一句话明确。
- 删除任何一句后若不影响理解或执行，则删除该句。
- 全文没有替研发决定内部实现。
