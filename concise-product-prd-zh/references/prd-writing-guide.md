# PRD 写作指南

## 1. 简介

### 1.1 背景

只写两类信息：

- **当前痛点：** 当前存在的产品或用户问题。
- **本次变更：** 本次准备调整的核心内容。

不单独介绍当前做法，不扩写痛点带来的业务或用户影响，不在背景中展开详细交互。

推荐句式：

> 当前存在【问题】。本次将【核心变化】，解决上述问题。

控制在一至三段。删除“随着业务发展”“为了提升体验”“进一步完善”等不提供事实的信息。

### 1.2 目标

说明本次改动希望达到的产品结果。

推荐句式：

> 通过【本次改动】，使【目标用户】能够【完成的行为】，达到【预期结果】。

目标通常一至三条。不要重复背景，也不要写接口改造、数据存储或代码重构等研发目标。

## 2. 产品概述

### 2.1 产品结构

说明本次需求涉及的角色、使用端、页面或功能模块及其关系。只保留理解本次需求所必需的结构，不扩展到无关的平台全景。

### 2.2 业务流程

按照用户完成任务的顺序说明：

1. 从哪里进入。
2. 执行什么操作。
3. 产品如何反馈。
4. 如何完成任务。
5. 必要的关键分支或失败结果。

流程描述用户行为和页面结果，不描述接口调用、数据读写和内部处理。多个端流程相同时合并表达，存在差异时只补充差异。

### 2.3 功能点

功能点是本次变更目录。每项只回答：

- 改什么。
- 用户最终能做什么。

推荐句式：

> 新增/调整【功能】，支持【用户行为】，并呈现【产品结果】。

一项功能点对应产品需求详解中的一项内容。不要在此展开默认状态、异常和详细操作，也不要把一个完整能力拆成多个零散动作。

## 3. 产品需求详解

按照功能点逐项展开。若有原型，将原型与对应规则放在一起；没有界面的功能不强制提供原型。

每项功能的业务规则以解释清楚功能为准，不另设“新增功能模块说明”。以下内容是写作参考，不是必须逐项填写的模板；可按场景合并、增加或省略，但不能遗漏影响功能理解的条件、操作和结果。

### 3.1 基本定义

按功能类型选择需要的信息：

- 组件类：组件类型、组件名称、使用位置、是否允许重复添加。
- 页面或普通功能：功能名称、使用角色、入口位置。

不适用的项目直接省略，不为满足格式强行填写。

### 3.2 业务规则与交互

用功能名称作为标题，按实际需要说明：

- 触发位置：用户从哪个页面或入口使用功能。
- 触发条件：何时生效、可操作或不可操作；自动发生的功能说明发生条件。
- 按钮：按钮名称、可用状态及操作结果。
- 交互逻辑：默认状态、用户操作、产品反馈，以及相关的取消、关闭、折叠、重新选择等操作；存在不同条件时分支说明。
- 弹窗文本：涉及弹窗时写清标题、正文、按钮及各按钮的操作结果；没有弹窗时不写。

简单功能可用一句话写清；复杂功能按条件或操作顺序组织。没有按钮或用户入口的功能不强行填写，展示、权限、限制和异常等内容仅在影响当前功能时补充。

推荐句式仅作参考：

> 在【位置】，满足【条件】时，用户点击【按钮】后，【产品结果】。

功能是否新增或调整、交互规则和弹窗文本均以需求材料、明确的版本差异或用户确认为依据。缺少依据或材料冲突时提出具体问题，确认前标记待确认，不自行猜测功能或文案。

只写用户能理解的产品行为，不写内部实现。原型已表达的静态布局不逐项复述，必要的交互规则仍需文字说明。

### 3.3 数据展示

按实际需要说明：

- 展示的信息及顺序。
- 单条和多条数据的展示方式。
- 数据之间的归属关系。
- 长文本的展开、收起或截断规则。
- 不同页面或使用端的相同点与差异。

字段较多时使用字段表或引用统一数据标准。PRD 不重复维护接口字段、平台映射和枚举定义。

### 3.4 空值和异常

只写用户可感知且与当前功能有关的状态，例如无数据、输入无效、获取失败、部分字段为空或无权限。

每种状态说明：

- 页面显示什么。
- 用户还能执行什么操作。
- 是否影响任务继续完成。

不写超时时间、错误码、重试次数、日志和异常捕获方式。没有相关异常时省略，不机械补齐状态表。

### 3.5 条件内容的归位

以下内容不是固定章节，只有影响当前功能时才写入对应需求详解：

- 权限与隐私：谁能看、默认展示什么、无权限时显示什么。
- 多数据边界：零条、一条、多条时的产品表现。
- 字段规则：名称、类型、默认状态和展示顺序。
- 状态规则：加载、成功、空值、失败和后续操作。
- 限制条件：可添加数量、操作前提和不可操作状态。

这些内容不能脱离功能单独堆砌，也不能转写成技术方案。

## 4. 数据兼容问题

从用户和产品使用角度回答：

- 已有数据或配置是否继续可用。
- 老用户是否需要重新操作。
- 历史内容继续如何展示。
- 新规则从何时开始生效。
- 新旧版本同时存在时，用户看到什么。
- 是否需要提供转换入口或提示。

推荐句式：

> 已有【数据/配置】保持原有展示和使用方式。本次调整仅影响【新建内容/后续操作】。用户编辑旧内容时，【提示或处理规则】。

若没有兼容影响，直接写：

> 本次调整不影响已有数据和历史内容。

不写数据库迁移、版本字段、任务脚本、幂等、回滚和审计实现。

## 产品职责边界

PRD 定义：

- 谁在什么场景使用。
- 用户可以做什么。
- 产品如何反馈。
- 展示什么内容。
- 有哪些限制和必要异常。
- 历史用户是否受影响。

PRD 不定义：

- 数据如何存储和传输。
- 接口、数据库和缓存如何设计。
- 前后端如何分工。
- 代码如何处理状态。
- 数据如何执行迁移。

判断方法：一句话描述“用户看到什么、能做什么、产品如何反馈”，通常属于产品规则；描述“系统内部怎么实现”，应移出 PRD。

## 精简规则

- 一句话只表达一条规则。
- 同一规则只出现一次。
- 原型表达布局，文字表达触发条件和状态变化。
- 删除不影响理解和执行的解释。
- 不使用“需要注意的是、为了更好地、从而进一步”等填充词。
- 不使用“可能、适当、大概、如有需要”等模糊词代替决策。
- 未确认内容集中标记为待确认，不混入确定规则。
- 同一对象使用同一名称；字段以指定标准为准。

## 常见错误

| 错误 | 调整方式 |
|---|---|
| 背景、痛点和目标重复 | 背景保留当前痛点与本次变更，目标只写产品结果 |
| 功能点写成详细规则 | 功能点只保留变更和用户能力，细节下沉到需求详解 |
| 每项功能都强填同一模板或另加新增模块说明 | 按实际场景说明条件、操作和结果，不适用项省略 |
| 弹窗只写“弹出提示” | 补充已确认的文本、按钮和操作结果；不确定时询问 |
| 原型旁逐项复述界面 | 只补充原型无法表达的交互、状态和限制 |
| 为所有需求强制增加权限、性能、验收等章节 | 只在相关功能中写实际存在的产品规则 |
| 用对象、数组、接口描述业务关系 | 改写成用户能理解的业务对象和页面结果 |
| 用技术方案解释历史兼容 | 只写旧内容是否可用、谁需要操作、用户看到什么 |
| 字段表和正文数量不一致 | 以指定标准为唯一来源，交付前核对名称和数量 |

## 最终审查

1. 四个一级模块是否齐全。
2. 背景是否只有当前痛点和本次变更。
3. 目标是否表达产品结果。
4. 每个功能点是否有对应需求详解。
5. 默认状态、操作结果、数据展示及必要异常是否明确。
6. 原型、文字、字段、数量和名称是否一致。
7. 数据兼容是否从用户角度说明。
8. 是否存在重复句、套话、模糊词或内部实现。
9. 删除任一句后若不影响理解或执行，删除该句。
10. 业务规则是否按实际功能组织，而非机械套模板；相关弹窗文本和按钮结果是否明确。
