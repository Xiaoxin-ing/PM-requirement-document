# PRD 写作指南

## 1. 简介

### 1.1 背景

只写两类信息：

- **当前痛点：** 当前存在的产品或用户问题。
- **本次变更：** 本次准备调整的核心内容。

不单独介绍当前做法，不扩写痛点带来的业务或用户影响，不在背景中展开详细交互。

推荐句式：

> 当前存在【问题】。本次将【核心变化】，解决上述问题。

控制在一至三段。删除“随着业务发展”“为了提升体验”“进一步完善”等不提供事实的信息。

### 1.2 目标

说明本次改动希望达到的产品结果。

推荐句式：

> 通过【本次改动】，使【目标用户】能够【完成的行为】，达到【预期结果】。

目标通常一至三条。不要重复背景，也不要写接口改造、数据存储或代码重构等研发目标。

## 2. 产品概述

### 2.1 产品结构

根据本次需求材料和用户提示，绘制并插入产品结构图，展示实际涉及的角色、使用端、页面和功能模块及其层级或归属关系。只保留理解本次需求所需的结构，不扩展到无关的平台全景，也不套用与当前需求无关的通用架构图。

结构图要求：

- 图中名称与原型、功能点和正文一致。
- 表达“属于哪里、包含什么、相互如何关联”，不要把用户操作步骤画成产品结构。
- 优先使用清晰的树状图或分层关系图；关系复杂时再使用连接线。
- 必须以可见图形插入最终文档，不能只提供 Mermaid 源码、文本树或外部链接。
- 材料不足以判断层级或归属时，先向用户确认，不自行补充产品模块。

### 2.2 业务流程

按照用户完成任务的顺序说明：

1. 从哪里进入。
2. 执行什么操作。
3. 产品如何反馈。
4. 如何完成任务。
5. 必要的关键分支或失败结果。

流程描述用户行为和页面结果，不描述接口调用、数据读写和内部处理。多个端流程相同时合并表达，存在差异时只补充差异。

### 2.3 功能点

功能点是本次变更目录。每项只回答：

- 改什么。
- 用户最终能做什么。

推荐句式：

> 新增/调整【功能】，支持【用户行为】，并呈现【产品结果】。

一项功能点对应产品需求详解中的一项内容。不要在此展开默认状态、异常和详细操作，也不要把一个完整能力拆成多个零散动作。

## 3. 产品需求详解

按照产品概述中的功能点逐项展开，每个功能使用独立的小节，标题采用“3.x 功能名称”。小节正文使用两列表格：

| 原型图 | 功能详细说明 |
|---|---|
| 嵌入该功能对应的实际原型图片 | 编写该功能的产品规则 |

### 原型图

- 将用户提供或已确认的原型截图、设计稿导出图直接嵌入左栏，保持内容可辨认。
- 同一功能包含多个关键状态或页面时，可在左栏按操作顺序纵向排列，并添加简短状态名称。
- 不得用原型链接、文件路径、文件名、HTML 文件或“见附件”等文字替代图片。链接可作为补充，但不能替代嵌入图。
- 图片只放与当前功能有关的页面或局部，避免把一张超长总图重复放进每个功能。
- 缺少界面功能所需的原型时，先向用户索取或确认可用材料，不自行臆造界面后作为正式原型。
- 无界面的规则类功能可在左栏明确标注“无界面原型”，但不能为了填表虚构页面。

### 功能详细说明

功能详细说明以解释清楚当前功能为准，不另设“新增功能模块说明”。以下内容是写作参考，不是固定模板，可按实际场景合并、增加或省略：

- 基本定义：组件类型、功能名称、适用角色、使用位置、是否允许重复添加等必要信息。
- 触发位置：用户从哪个页面或入口使用功能。
- 触发条件：何时生效、可操作或不可操作；自动发生的功能说明发生条件。
- 按钮：按钮名称、可用状态及操作结果。
- 交互逻辑：默认状态、用户操作、产品反馈，以及取消、关闭、折叠、重新选择等反向操作；存在不同条件时分支说明。
- 弹窗文本：涉及弹窗时写清标题、正文、按钮及各按钮的操作结果；没有弹窗时不写。
- 数据展示：必要的展示内容、顺序、归属关系、多条数据和长文本规则。
- 空值和异常：用户可感知的无数据、输入无效、获取失败、字段为空或无权限状态，以及用户能否继续操作。

简单功能可以用数条规则写清；复杂功能按条件或操作顺序组织。字段较多时使用字段表或引用统一数据标准。权限、边界、限制和异常只在影响当前功能时说明，不机械补齐。

#### 组织方式与编号

- 每组内容先写一个能说明主题的短标题，再写对应段落或分点，不能在说明栏开头直接堆放无标题的列表。
- 标题根据当前功能选择，可使用“功能说明”“交互逻辑”“展示说明”等，也可改用“查询逻辑”“信息带入”“提交校验”等更准确的名称；不要求每项功能都出现同一组标题。
- 同一功能可以混用简短段落和编号。能用一句话讲清的内容直接写在标题下，需要拆分操作、条件或结果时再编号。
- 一级分点使用 `1. 2. 3.`；一级条目存在下属规则时，二级使用 `a. b. c.`；二级条目仍需细分时，三级使用 `i. ii. iii.`。
- 只有真实的包含、条件或步骤从属关系才使用多级编号。平行内容保持 `1. 2. 3.` 单层，不为排版增加空层级。

示例：

**交互逻辑**

1. 点击入口后打开选择面板。
2. 关闭面板：
   a. 点击关闭按钮时关闭面板。
   b. 点击面板外区域或按 `Esc` 时关闭面板。

**展示说明**

1. 默认展示完整列表。
2. 搜索后只展示匹配结果。

功能是否新增或调整、交互规则和弹窗文本均以需求材料、明确的版本差异或用户确认为依据。缺少依据或材料冲突时提出具体问题，确认前标记待确认，不自行猜测。

只写用户能理解的产品行为，不写接口、数据库、事件、存储或其他内部实现。原型已表达的静态布局不逐项复述，必要的交互规则仍需文字说明。

## 4. 数据兼容问题

从用户和产品使用角度回答：

- 已有数据或配置是否继续可用。
- 老用户是否需要重新操作。
- 历史内容继续如何展示。
- 新规则从何时开始生效。
- 新旧版本同时存在时，用户看到什么。
- 是否需要提供转换入口或提示。

推荐句式：

> 已有【数据/配置】保持原有展示和使用方式。本次调整仅影响【新建内容/后续操作】。用户编辑旧内容时，【提示或处理规则】。

若没有兼容影响，直接写：

> 本次调整不影响已有数据和历史内容。

不写数据库迁移、版本字段、任务脚本、幂等、回滚和审计实现。

## 产品职责边界

PRD 定义：

- 谁在什么场景使用。
- 用户可以做什么。
- 产品如何反馈。
- 展示什么内容。
- 有哪些限制和必要异常。
- 历史用户是否受影响。

PRD 不定义：

- 数据如何存储和传输。
- 接口、数据库和缓存如何设计。
- 前后端如何分工。
- 代码如何处理状态。
- 数据如何执行迁移。

判断方法：一句话描述“用户看到什么、能做什么、产品如何反馈”，通常属于产品规则；描述“系统内部怎么实现”，应移出 PRD。

## 精简规则

- 一句话只表达一条规则。
- 同一规则只出现一次。
- 原型表达布局，文字表达触发条件和状态变化。
- 删除不影响理解和执行的解释。
- 不使用“需要注意的是、为了更好地、从而进一步”等填充词。
- 不使用“可能、适当、大概、如有需要”等模糊词代替决策。
- 未确认内容集中标记为待确认，不混入确定规则。
- 同一对象使用同一名称；字段以指定标准为准。

## 常见错误

| 错误 | 调整方式 |
|---|---|
| 背景、痛点和目标重复 | 背景保留当前痛点与本次变更，目标只写产品结果 |
| 功能点写成详细规则 | 功能点只保留变更和用户能力，细节下沉到需求详解 |
| 产品结构只写一段文字或套通用图 | 根据本次需求范围绘制并嵌入实际产品结构图 |
| 需求详解只写功能说明或原型链接 | 每项功能使用“原型图｜功能详细说明”两栏并嵌入实际图片 |
| 每项功能都强填同一模板或另加新增模块说明 | 先用符合内容的短标题分组，再说明必要的条件、操作和结果；不适用项省略 |
| 说明栏直接堆放无标题的列表 | 先说明每组内容的主题，再按实际从属关系使用 `1. / a. / i.` 分级 |
| 弹窗只写“弹出提示” | 补充已确认的文本、按钮和操作结果；不确定时询问 |
| 原型旁逐项复述界面 | 只补充原型无法表达的交互、状态和限制 |
| 为所有需求强制增加权限、性能、验收等章节 | 只在相关功能中写实际存在的产品规则 |
| 用对象、数组、接口描述业务关系 | 改写成用户能理解的业务对象和页面结果 |
| 用技术方案解释历史兼容 | 只写旧内容是否可用、谁需要操作、用户看到什么 |
| 字段表和正文数量不一致 | 以指定标准为唯一来源，交付前核对名称和数量 |

## 最终审查

1. 四个一级模块是否齐全。
2. 背景是否只有当前痛点和本次变更。
3. 目标是否表达产品结果。
4. 每个功能点是否有对应需求详解。
5. 产品结构是否根据本次需求绘制并以图形插入，且层级、归属和名称准确。
6. 每项界面功能是否使用“原型图｜功能详细说明”两栏，并嵌入可辨认的实际原型图片。
7. 默认状态、操作结果、数据展示及必要异常是否明确。
8. 原型、文字、字段、数量和名称是否一致。
9. 数据兼容是否从用户角度说明。
10. 是否存在重复句、套话、模糊词或内部实现。
11. 删除任一句后若不影响理解或执行，删除该句。
12. 功能详细说明是否先按内容分组再编号，且没有机械套用同一组标题；多级编号是否只用于真实从属关系。
13. 相关弹窗文本和按钮结果是否明确。
